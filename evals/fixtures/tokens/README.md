# Design tokens fixture

`design-tokens.json` is a dummy, self-consistent 3-tier token file (DTCG format, per `references/design-tokens-format.md`) — primitive → semantic → component. It exists purely for the blind-implementation testing environment, not as skill guidance: it's a stand-in for "the design system's actual token file" that a real coded reference (Phase 2 Path B) would extract from.

## Why it exists

Most of the eval contracts (`evals/evals.json`) have a pending or partial Token Map, because the hand-fed interview transcripts either said "description only" or invented a handful of token names inline (e.g. Modal's `--color-overlay-backdrop`). Those inline names were never derived from anything real — they were just plausible-sounding strings typed into an eval prompt. This file gives us an actual, independently-built tree to check contracts against, so a mismatch is a genuine finding, not something rigged into the test.

## How to use it

1. **As a resource for blind implementers.** When a contract's §4.3 Token Map is pending or only partially bound, hand this file to the blind-implementer agent alongside the contract, the same way a real engineer would reach for the design system's token file even when the specific component's own contract hasn't cited one yet. Do not tell the implementer which tokens "should" apply — let them look it up and flag anywhere the contract's stated intent (a color, a radius, a spacing value) doesn't map cleanly onto anything in the tree.
2. **As ground truth for re-running Phase 2.** For a more direct test, re-run a contract's token extraction (Phase 2 Path B) against this file as the coded reference, instead of the ad hoc inline answer the original eval prompt gave. Compare the newly-derived Token Map against what's already in the contract — a divergence is either a real coverage gap (Phase 2 missed something extractable) or a naming-convention mismatch worth surfacing via the Conflict resolution policy.

## What already doesn't line up (found by building this file independently, not engineered)

- **Modal's three canonical token names don't match the tree's naming shape.** Modal's contract has `radius-modal` and `spacing-modal-padding` (component name as a *suffix* or embedded mid-string); the tree consistently prefixes every component token with the component name first (`modal.radius`, `modal.body-padding`). Same concepts, different convention — exactly the kind of thing Modal.md's own "no naming convention was confirmed for this component" caveat correctly hedged against, rather than overclaiming a match it couldn't verify.
- **Toast/Snackbar's auto-dismiss timing is correctly absent from this file.** An early version of this fixture modeled the "5 seconds before auto-dismiss" value as a `motion.duration` token, which was a category error: a *motion* duration (`component.toast.enter-duration`, below) governs how a transition animates and is a real token; an *interaction/lifecycle* duration (how long before the toast disappears on its own) determines whether and when a DOM change happens, not how it renders — that's a Behavioral Prop (§3.3, a numeric operational option with a default), the same category as `loading`/`disabled`, not something to look up here. Toast.md and Snackbar.md should carry it as a prop like `dismissTimeoutMs` (default `5000`), not a token reference.
- **Badge's confirmed naming convention checks out.** Its Q9 example, `color-surface-neutral`, is a near-exact match (dot-to-kebab) for the tree's real `semantic.color.surface.neutral` — good evidence the convention it gave is a real one, not invented.
- **Snackbar's tree entry independently confirms a contract decision.** The tree gives Snackbar one fixed dark surface color rather than per-severity semantic colors, which lines up with §3.2 being omitted outright in Snackbar.md ("only one visual treatment exists") — cross-confirmation from an independently-built source, not the same reasoning reused.

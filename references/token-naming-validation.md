# Token-name validation — checking a generated implementation's names against the token tree

Source of authority: none external — this is a synthesized algorithm, not a citation of an existing spec. It exists because no naming-transform tool (Style Dictionary or otherwise) exposes one universal downstream convention to check against; every design system configures its own. This file is the mechanism for checking a name against the *shape* of the canonical token tree without needing to know that system's specific convention in advance.

**Last verified:** 2026-09-06

## What this replaces: nothing

This does not generate tokens, transform names, or stand in for Style Dictionary or any equivalent pipeline. The skill's entire involvement with tokens is to **state** a token's canonical identity in the contract and **validate** that a real generated variable — a CSS custom property, a Swift constant, an Android resource — corresponds to it. The pipeline that produced that variable sits in between and is never the thing being checked, exactly as SKILL.md's "Native platform technology as the stated level" treats the framework that produced a rendered DOM node.

That boundary is why the precondition below is a gate and not a preference: with no pipeline, there is no generated variable, so the check has no subject.

## Vocabulary

Three facts, kept distinct throughout this file (see SKILL.md's "Three naming facts"):

- **Canonical path** — the token's identity, one per token: `ds.semantic.color.bg.surface`.
- **`naming-pattern`** — the slot schema this tree's canonical paths follow, recorded as `tokens.patterns` in `.claude/design-system-context.yml`: **a list of templates, one per path shape, per tier** — a real tree commonly has several (`component.{component}.{property}` and `component.{component}.variant.{variant}.{property}` in the same system). Proposed by `scripts/detect_tokens.py` and confirmed in Phase 0B.
- **Naming convention** — how one *platform's* generated output renders a canonical path, one per platform, three independent axes: separator/case row, added prefix, scope depth.

**`namespace`** keeps its narrow meaning here throughout: the *leading* segments a platform's pipeline scopes away. It is never a synonym for the canonical path.

## Precondition — this only applies when hand-typed values are already out of scope

This validation assumes the design system's own policy is that no component hand-types a token's resolved value or invents its own alias name for one — token values are generated downstream (Style Dictionary or an equivalent pipeline) from the canonical tree, and components consume the generated, named result. That assumption is recorded once, system-wide, as `tokens.generated_downstream` in `.claude/design-system-context.yml` (see SKILL.md's Phase 0B schema) — never re-derived per component, and never assumed true by default for a design system that hasn't confirmed it.

**If that precondition doesn't hold** (the design system hand-types values as accepted practice, or hasn't set up generation), this validation does not apply, and nothing here should be run as a fallback or a lesser substitute. A hand-typed literal has no name to check in the first place — see SKILL.md's Conflict resolution policy case 4 ("no source covers this case") for how to record that plainly instead of forcing a check that doesn't fit. This file's job is strictly to validate *names* generated by an already-trusted pipeline; it never re-verifies that pipeline's own value correctness, and it never becomes an alternative to running one.

## The core idea: generate known forms, don't parse the candidate

A candidate name like `primitivecolorpurple500` has no delimiters left to split on — there is no reliable way to reverse-parse it back into words. The reliable direction runs the other way: take the token's own canonical path, generate every commonly-used naming convention's form of it, and check whether the candidate matches one of those generated forms exactly. Reject-by-construction follows for free — a candidate with the words in the wrong order, or a substituted word, can never match anything that was generated by preserving both. (Verified against a real tree: `--primitive-color-500-purple` and `--base-color-purple-500` both fail at every row and every depth.)

**What this does not give you for free is *which* token matched.** Generation guarantees a matching candidate preserves some canonical suffix in order — it does not guarantee that suffix belongs to only one token. Past a certain truncation depth it belongs to several, and the check silently passes a wrong binding. Step 4 covers when a depth is safe to lock and when it isn't.

## Step 1 — canonicalize the token path into an ordered list of atomic words

Two levels of splitting, not one: the token tree's own tier separator (`.`), *and* any separator already inside one tier segment (multi-word segments like `primary-hover` exist in the tree itself — see `design-tokens-format.md`'s tiering conventions for why primitive/semantic/component segments look the way they do).

```
"primitive.color.purple.500"
  split on "."             → ["primitive", "color", "purple", "500"]
  split each on "-" / "_"  → (no change — no segment here has an internal separator)
  lowercase every word     → ["primitive", "color", "purple", "500"]
```

A token whose path is `semantic.color.action.primary-hover` splits further at the last segment: `["semantic", "color", "action", "primary", "hover"]`. This flat word list, in this exact order, is the one invariant every valid name must preserve, however much of it a given system's pipeline chooses to keep — see Step 4 for what "chooses to keep" means. Order exists to convey hierarchy, in whatever slot sequence this design system's `naming-pattern` defines — `prefix.tier.property.element.level` and `tier → category → concept → scale step` are two possible patterns, not the universal one. This step reads that order off the tree directly, so it doesn't have to be told the pattern in order to compare one name; the pattern is what makes the comparison *meaningful* rather than merely mechanical, and what lets a mismatch be reported as the slot that moved. Whatever the pattern, nothing downstream is allowed to reorder it, only to truncate it from the front.

## Step 2 — generate every known convention's form from that word list

The space of real-world naming conventions is small and enumerable — a product of separator and case, not an open-ended set:

| Convention | Separator | Case | Generated form (from the example above) |
|---|---|---|---|
| dot-path | `.` | lower | `primitive.color.purple.500` |
| kebab | `-` | lower | `primitive-color-purple-500` |
| snake | `_` | lower | `primitive_color_purple_500` |
| camel | none | first word lower, each following word capitalized | `primitiveColorPurple500` |
| pascal | none | every word capitalized, including the first | `PrimitiveColorPurple500` |
| flat | none | lower | `primitivecolorpurple500` |
| screaming snake | `_` | upper | `PRIMITIVE_COLOR_PURPLE_500` |

A numeric segment (`500`) has no case of its own — it's appended as-is regardless of which row is being generated; it never triggers a capital letter or an extra separator in the camel/pascal/flat rows.

A structural prefix required by file syntax (CSS custom properties must start `--`) is applied on top of whichever row is being generated — it's a property of the file type, not an eighth convention. A project-specific branding prefix (`ds-`, `brand-`) is different: it's an extra word not present in the canonical path at all, so it can't be produced by this table — it has to be detected empirically (Step 4) before generation can account for it.

## Step 3 — per-name check, against every truncation of the word list

A candidate is checked against each row of Step 2's table applied to the **full word list first, then each contiguous leading-truncation of it** — the full list, then the list with word 1 dropped, then words 1–2 dropped, and so on. Truncation is only ever from the front (see "Why only leading truncation" below), so whatever remains is always a real suffix of the canonical order — reordering or substituting a word can never produce a match at any truncation depth, for the same reason it couldn't before: nothing generates those shapes.

A candidate is valid if it exactly equals the generated form of *some* row at *some* truncation depth. The depth at which it matched (0 = nothing dropped) is recorded alongside the row — both numbers matter to Step 4.

**Why only leading truncation.** A namespace is a prefix concept — dropping `primitive.color` because the file you're in already scopes everything to `color` is a real, common pattern (Style Dictionary configs routinely strip leading path segments this way). Dropping a *middle* word (`purple` vanishing while `primitive`, `color`, and `500` remain) isn't scoping, it's a different word — that's indistinguishable from an abbreviation or a typo, which this file deliberately does not try to accommodate (see the fails list below). Restricting truncation to the front is what keeps those two cases apart.

## Step 4 — lock the naming convention on first success: all three of its axes

The first name checked for a given platform fixes three things at once, not just the separator/case row:
1. **The row** (kebab, camel, flat, …).
2. **A custom prefix**, if the name only matched after stripping one beyond the mandatory file-type prefix (`ds-`, `brand_`) — never guessed without a name that confirms it.
3. **The truncation depth** that produced the match — how many leading canonical words this platform's pipeline consistently omits.

All three get written to `design-system-context.yml`'s `naming_convention` for that platform once confirmed, so later components skip re-detection the same way framework detection already does.

**The lock must come from a name already known to be correct, and must be confirmed before it is written down — at every depth, including depth 0.** This is the single most consequential moment in the whole check: whatever is locked here becomes the standard every later name in every later component is judged against. If the name that sets it is itself wrong, the lock inverts the check — every subsequently *correct* name is then reported as `Inconsistent convention`, and the one genuinely broken name is the only thing that passes. A check that reports correct work as broken is worse than no check, so never lock silently on an unverified first name.

**If the first name only matches at depth > 0**, say so specifically when asking for that confirmation — namespace scoping is a real, plausible convention, not a defect, but it is a new fact about this platform: *"This platform's generated names omit the leading segment(s) `{dropped words}` — confirm this scoping is intentional before it's locked in."*

### Two ways the first name can fail to determine a lock

Both were found by running this algorithm against a real 162-token tree (`evals/fixtures/tokens/design-tokens.json`); neither is hypothetical.

**1. The name matches several rows at once — don't lock the row.** Short generated forms are frequently ambiguous: at the truncation depth where only one word remains, `white` is simultaneously a valid `dot`, `kebab`, `snake`, `camel`, and `flat` rendering, because none of those separators or capitalizations have anywhere to appear. A purely numeric tail like `40` matches **all seven rows**. In that fixture, 109 forms match 5 rows and 53 match all 7.

A name matching more than one row confirms nothing about which row is in use. **Lock on the first *unambiguous* success, not simply the first success** — a multi-row match is consistent with the tree and must not be reported as a finding, but it carries no information, so record it as a pass and keep looking for a name that resolves the row. If a whole run produces only ambiguous names, no row gets locked and none should be invented; report that the convention is still undetermined.

**2. The depth is only usable if names stay distinct at it — check before locking.** Leading truncation discards the very segments that distinguish tokens from one another, so past a certain depth different tokens collapse onto the same generated name. Measured on that fixture:

| Locked depth | Distinct names (of 162 tokens) | Ambiguous tokens |
|---|---|---|
| 0 | 162 | 0 |
| 1 | 162 | 0 |
| 2 | 155 | 10 |
| 3 | 101 | 68 |
| 4 | 31 | 131 |

At depth 0–1 the mapping is injective and the check is sound. From depth 2 it isn't: `component.button.radius`, `component.badge.radius`, and `component.toast.radius` all render as `radius`. That breaks the check's actual purpose — a contract binding `component.button.radius` against an implementation that references `component.toast.radius` would **pass**, because both produce the same string.

So before locking any depth > 1, generate every token in §4.3.2's Token Map at that depth and confirm they are all distinct. If any two collide, the depth is unusable for validation regardless of whether the pipeline really uses it: report that this platform's naming discards too much to verify bindings, and check nothing rather than reporting false passes. Note which failure this is — silently passing a wrong binding is the one outcome this file exists to prevent.

**These two conditions are independent — evaluate both and report every one that applies, rather than stopping at the first.** A single name is frequently both: `radius`, checked against `component.button.radius`, is ambiguous across five rows *and* sits at a depth where three different tokens collapse onto it. Reporting only the ambiguity ("keep looking") would send someone hunting for a disambiguating name at a depth where no valid one can exist, since every token there is equally collapsed. Depth verifiability is a property of the Token Map at that depth, not of the individual name, so it is checked whether or not that name happens to determine a row.

## Step 5 — every subsequent name is checked against all three locked facts, not re-detected

For every other name checked in the same build:
- Matches the locked row, prefix, and **exactly** the locked truncation depth → pass.
- Matches the locked row and prefix, but at a **different** truncation depth than what's locked → **alert**, distinct from and more severe than a plain mismatch: *"Inconsistent scoping — this name omits {N} leading segment(s), but this platform is locked to omitting {M}."* This is the case that actually matters most to catch: individually, a depth-2 name and a depth-0 name might each look like a valid, well-formed reference in isolation, so only checking against the locked depth (not just "some valid depth") surfaces the drift.
- Matches a **different row** than the locked one (regardless of depth) → the existing inconsistent-convention failure, unchanged from before.
- Matches no row at any depth → structural mismatch or unknown token, per the table below.

## Failure and warning categories — report which one, not just "mismatch"

| Finding | Severity | Cause | Example |
|---|---|---|---|
| Unknown token | Alert | The word sequence doesn't correspond to any path in the token tree at all, at any truncation depth | referencing a token that doesn't exist, or a typo severe enough to change the words |
| Structural mismatch | Alert | The right token's words exist, but reordered, or with a word substituted, or a *non-leading* word missing. Where a `naming-pattern` is on record, report which slot moved ("puts `level` before `element`; this system's `naming-pattern` is `…element.level`") rather than a bare "reordered" | `--primitive-color-500-purple` (reordered), `--base-color-purple-500` (`base` isn't `primitive`) |
| Inconsistent convention | Alert | The name matches a real token's word sequence, under a row *other than* this build's locked row | `--primitive_color_purple_500` appearing in a build already locked to kebab-case |
| Inconsistent scoping | Alert | The name matches the locked row, but at a truncation depth other than the one locked for this platform | a depth-2 name appearing in a platform locked to depth-0 |
| Namespace scoping detected | Warning, once, then locked | The *first* name checked only matches at depth > 0 | `--color-purple-500` as the very first name checked, confirming `primitive` is consistently dropped |
| Row undetermined | Not a finding — a pass that carries no information | The name matches the tree at more than one row, so it can't fix the convention | `white`, valid as dot/kebab/snake/camel/flat at once; `40`, valid as all seven |
| Depth not verifiable | Alert, and the check stops for this platform | Two or more Token Map entries generate the same name at the candidate depth, so a correct and an incorrect binding are indistinguishable | at depth 2, `component.button.radius` and `component.toast.radius` both render `radius` |

Only the last row is a warning rather than an alert — it's the one case where the finding is "a new, plausible fact needs confirming," not "something is actually wrong."

## Worked example

Token: `primitive.color.purple.500` → canonical words `["primitive", "color", "purple", "500"]`.

**Passes at depth 0** (each matches one table row exactly, full word list):
`primitive.color.purple.500`, `--primitive-color-purple-500`, `primitive_color_purple_500`, `primitiveColorPurple500`, `PrimitiveColorPurple500`, `primitivecolorpurple500`, `PRIMITIVE_COLOR_PURPLE_500`

**Passes at depth 2, if locked** (the `primitive`/`color` prefix dropped, `purple`/`500` intact and in order): `--purple-500`, `purple_500`, `Purple500`

**Fails, and why:**
- `--primitive-color-500-purple` — structural mismatch (reordered; no truncation depth produces this shape)
- `--base-color-purple-500` — structural mismatch (`base` isn't a canonical word at any depth)
- `--primitive-color-purple-500` followed elsewhere in the same build by `--primitive_color_purple_500` — inconsistent convention (second name, different row)
- `--purple-500` followed elsewhere in a build locked to depth 0 by `--color-purple-500` — inconsistent scoping (different depth than locked, even though each would independently look plausible)

## What this deliberately does not check

This validates the *style logic* — that the token named in a real implementation is the token the contract stated. It is a check on the reference chain, not on anything at the end of it.

- **Not the value behind the token.** If `semantic.color.bg.surface` aliases to a grey someone later judges wrong, that is a design decision recorded in the tree, not a naming defect. The reference is correct and this check passes — correctly. Re-deriving value correctness would mean second-guessing the design system's own tree, which is the one thing SKILL.md's Conflict resolution policy explicitly treats as authoritative.
- **Not the resolved output of the pipeline.** Whether Style Dictionary (or an equivalent) emitted the right literal for the right platform is that tool's job. This never re-verifies a pipeline it presupposes.
- **Not the rendered result.** Whether the component actually *looks* right is visual regression testing's job, and it answers a different question. Note the two are not redundant: a wrong-but-plausible token reference can render something that looks entirely acceptable, passing visual regression while the style logic is broken. That gap is precisely what this check covers, and why it isn't made obsolete by having good screenshot tests.

The inverse also holds, and is worth stating because it looks counterintuitive: a component that renders correctly while referencing a token the contract never stated **is** a finding here. Nothing is visibly wrong; the logic connecting intent to implementation is.

This mirrors `structural-fact-validation.md`'s closing boundary — that file confirms the right node exists with the right role, not that a screen reader announces it usefully. Same division: these checks establish that what was specified is what got built, never that what was specified was a good idea.
